# Capability registry and ranking

`model-registry.cjs` stores provider metadata in `front-office-catalog.json` under the existing app-data directory. Refresh is explicit and provider-scoped. OpenRouter metadata includes modalities, advertised context/output limits, supported parameters and prices converted from USD/token to USD/million tokens. NVIDIA's current catalog supplies IDs; missing limits/prices/features remain null or `unknown`. Neither listing proves account inference access or quota.

Profiles distinguish logical model ID, provider ID and deployment ID (`provider:model`). Logical IDs are not guessed across vendors; users can override them with provenance when they know two deployments represent the same underlying model. Overrides are validated, locally inspectable, timestamped and stored separately from the original provider catalog, surviving refresh. Reset removes the override. Credential configured status is read separately and never includes a key. Favorites are non-secret local preferences.

The Settings capability catalog supports provider, text/vision/tools/structured-output, minimum advertised context, measured-only, configured-key, favorite and sample-budget filters. Sorts include selected-task quality, advertised context/output, estimated sample price, TTFT, success-rate reliability, provider and alphabetical order. The common pure sorter has stable deployment-ID ties. Default match uses fresh measured task quality when available; otherwise capability coverage, advertised context and output. Unknown quality displays `Not tested`, never a fabricated benchmark rank. Price comparison uses a labeled sample of 1,000 input and 256 output tokens. Stale/unknown prices cannot pass the affordability filter.

The inspector shows endpoint, original/effective provenance, supported parameters, limits, task-specific methodology, last test, timing/success evidence, local failure/circuit state and editable override JSON. A provider connection check is not substituted for a quality benchmark. Example override (replace values only with supported metadata):

```json
{"contextTokens":32768,"maxOutputTokens":4096,"structuredOutput":false}
```

`long-context-reliability.cjs` only considers matching deployment/model version, task, transport, repeated observations and fresh timestamps. Imported records contain benchmark, dataset, methodology, position, context length/measurement source, score, repetitions and uncertainty. A tested retrieval bound is reported only for actual provider-counted lengths with beginning/middle/end coverage and perfect exact-retrieval results. This conservative descriptive rule is not a general reliability guarantee and never extrapolates to the advertised maximum. The default for unverified context is warn; strict and allow are explicit alternatives. Mock benchmarks generate no production evidence records.

Routing first checks permitted providers, configured credentials, circuit state, text modalities, structured-output support, supported generation parameters and token/cost capacity. Auto mode requires known advertised context/output limits; manual mode can use the explicitly configured bound when provider capacity is unknown, with a warning. Stale metadata cannot justify auto routing or a cost cap. Manual session pins either execute that exact deployment or reject. Changing global auto settings does not unpin an existing manual conversation.

Eligible auto candidates use the configured priority/weights. Balanced score is `quality*wQuality + priceUtility*wCost + speedUtility*wLatency + successRate*wReliability`; price utility is `1/(1+estimatedRequestUsd)`, speed utility is `1/(1+ttftMs/1000)`. Missing measurements contribute no utility and remain unknown in the inspector. Quality/speed/cost priorities use their respective utility. Ties use capability coverage, context capacity and stable deployment ID. Rationale, warnings, eligibility and rejection reasons are emitted before inference.

Fallback exists only in auto mode when enabled. A separate `allowCrossProviderFallback` consent flag is required to send experiment questions/history to another provider, even when both providers are listed. It stays within the explicit allowed-provider list; alternate models additionally require `allowModelSwitch`. Without that flag, only equal logical-model IDs can be fallbacks. Every attempt/deployment switch is visible in the UI and JSON trace. No scheduler refreshes metadata or runs benchmarks in the background.
