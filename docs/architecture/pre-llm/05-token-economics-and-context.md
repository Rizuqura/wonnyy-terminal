# Token budgets and conversation boundaries

Experimental conversations use schema 5 in the existing `.wonnyy/conversations/` store, with explicit `mode: front-office`; experimental runs use schema 3 in `.wonnyy/model-runs/`. Existing agent schemas and their context provenance are unchanged. The two execution entry points reject each other's conversation mode. Recovery reuses pending run references; request-ID replay returns an existing result instead of another provider call. Explicit retry reuses the latest failed user turn, while new questions create new turns. A new experiment resets history by creating a new conversation; deletion removes only that experiment snapshot, retaining immutable run records.

The request contains no Context Box, agent ID/instructions, tools, skill guidance, RAG or persistent-memory input. Unknown fields are rejected. There is no injected system prompt and no model call to classify a request. Requirements derive from the explicit task, text modality, requested format and configured policy. Unmeasured reliability/latency targets remain null.

All successful user/assistant exchanges are included before the latest question. Failed attempts contribute no successful answer. Nothing is silently dropped, summarized or compressed. The local safety boundary permits up to 128 messages, 2,000,000 history characters and 200,000 characters for a new question; exceeding those limits rejects before dispatch. This accommodates controlled 25-turn tests. Characters, estimated tokens, provider counts and output caps are separate quantities.

The estimator reuses the existing UTF-8-byte heuristic (`ceil(bytes/3) + 12` per message); it is approximate and not a verified model tokenizer. The effective capacity is the smaller of the configured context bound and known advertised context. Preflight reserves `ceil(capacity * headroomFraction)` plus the requested output cap and rejects when full input + output + headroom exceeds capacity. Advertised output limits are checked independently. An unknown model limit is not relabeled as a measured capability.

If both prices are known and fresh, the preflight estimate uses input estimate plus the full output cap. A hard estimated USD cap rejects unknown/stale prices. A total-token cap and USD reservation are cumulative across attempts; another retry is refused before spending if its reservation would cross a cap. These are conservative client estimates, not guarantees about actual provider billing or a model-specific tokenizer. Failed streams may be charged without reporting usage; exports label missing coverage rather than treating it as zero cost.

Runtime metrics preserve reported prompt/output counts and separately expose reasoning-token details when supplied. Reasoning can share an output budget depending on the provider; no extra undisclosed reasoning allowance is requested. Reported output above the configured cap is rejected. `length`/refusal/other incomplete finishes remain legible failures with their finish reason retained in per-call metrics. The client cannot physically prevent a provider from disregarding requested limits; use provider-side credit/quota controls when an absolute billing ceiling is required.

JSON output is requested only for deployments with explicitly supported structured output. Local validation supports `type`, `properties`, `required`, boolean `additionalProperties`, `items`, `enum` and `description`, with maximum schema depth 10. Unsupported schema keywords are rejected before dispatch. Invalid JSON or schema mismatch is labeled as a validation failure; no hidden repair call claims compliance.
